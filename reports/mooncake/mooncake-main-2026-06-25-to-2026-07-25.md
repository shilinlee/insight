## 重点摘要

过去一个月 Mooncake 的主线工作从上一期的“能力补齐”进一步转向 **传输意图与 QoS 调度落地**、**Store 多租户和分层存储生产化**、**结构化对象接口成型**、**异构互联与发布体系扩展** 四个方向。

1. **TENT 开始具备面向请求目标的调度闭环**：请求侧新增 `IntentType`、`deadline_ns` 和 `policy_name`，调度侧加入最早截止时间优先、临近截止时间提级、不可满足请求降级、按策略分配 SL/TC/QP pool、实时 RDMA 带宽反馈和传输级指标，TENT 正从传输抽象层演进为可观测、可降级的 QoS 调度层。
2. **Store 多租户从 quota 功能走向统一身份和严格准入**：新增严格多租户 quota admission、可配置 tenant id、etcd quota connector、canonical `TenantId`、host segment quota pinning，并拆分 tenant quota table。这些改动让租户身份、容量配额和资源固定形成更一致的控制链路。
3. **SSD/L2 分层缓存重点补强一致性和恢复能力**：新增主动磁盘水位驱逐、L2→L1 热点提升后台重试、OffsetAllocator FIFO 驱逐与可持久化恢复，并修复 publish-before-commit、RemoveAll 残留文件、驱逐回滚和 snapshot 容量序列化等问题，体现出本期重点已从“支持 SSD”转向“长期稳定运行 SSD”。
4. **Python wheel 的结构化对象能力形成统一接口**：从 flat MVP 演进到统一 put/get、多 buffer 写入、pool-backed 读取、schema-guided `DataProto` 编码和非 tensor codec，且恢复多 buffer payload 的 zero-copy 写入，面向推理框架的复杂对象交换能力更完整。
5. **异构传输覆盖和可靠性同步增强**：新增 TPU/PJRT staging、HPE Slingshot/CXI、MNNVL Device API、AMD `rdma+hip` 多协议与 MUSA/DeepEP V2 能力；同时集中修复 RDMA rail failover、QP 生命周期、GPU 设备选择、NVMe-oF/GDS 错误传播等生产边界。
6. **工程化和文档进入规模化维护阶段**：发布 wheel 覆盖 EFA、MUSA、aarch64、多 CUDA/PyTorch 组合，文档新增 Kubernetes、llm-d、多模型 KV 隔离、SGLang/vLLM benchmark，并重组导航和性能文档，项目交付面明显扩大。

## 新特性与产品能力

### 1. TENT 传输意图、截止时间和 QoS 调度形成体系

本期 TENT 的新增能力围绕“请求希望如何被传输”展开。`Request` 新增 `IntentType`，并把 `deadline_ns`、`policy_name` 暴露到 Python；SelectionPolicy 可以绑定 intent type，并配置独立的 SL、TC 与 QP pool。admission queue 则增加最早截止时间优先、按截止时间临近程度提级、不可满足请求丢弃与降级 hook，以及基于实时 RDMA NIC 带宽的降级决策。

这批变化把请求描述、策略选择、队列派发和资源分配串成一条链路。上层不再只能选择某种 transport，而可以表达延迟目标和策略意图；底层则可以结合 deadline、优先级、链路负载和网络服务等级作出决策，为多业务共享传输资源提供基础。

TENT 的可观测性也同步增强：增加 MLU 指标、QoS metrics baseline、因果链阶段延迟拆分、per-transport labels、RDMA NIC load stats 和 mixed traffic workload。相比只看总吞吐，这些指标更适合定位排队、策略选择、传输执行和硬件链路中的具体瓶颈。

### 2. Store 多租户身份、配额与资源控制继续收敛

Store 新增 strict multi-tenant quota admission，使超出配额的请求能在准入阶段被明确限制；client tenant id 变为可配置，并加入 etcd tenant quota connector。后续提交又引入 canonical `TenantId`、tenant id 热路径的零拷贝规范化、host segment quota pinning，并把 tenant quota table 从 MasterService 中抽离。

综合来看，多租户能力正在从散落的字符串、配置和计数逻辑，收敛到统一身份类型、外部 quota 来源、严格准入以及资源固定机制。对共享 Store 集群而言，这有助于减少身份格式不一致、quota 绕过和跨租户资源争用，也让后续独立演进 quota 管理组件更容易。

### 3. 分层存储增加主动治理和重启恢复能力

SSD/本地盘方向新增 proactive disk watermark eviction，可在磁盘达到水位时主动释放空间；OffsetAllocatorStorageBackend 增加 FIFO eviction，并支持可配置持久化，使 allocator 能在重启后恢复。L2→L1 promotion 则增加对仅存在于 LOCAL_DISK 的热点 key 的后台重试，提升热数据重新进入内存层的成功率。

本期还补齐了 local-first allocation、拓扑感知的远端 replica 评分、SSD benchmark 多线程与回放加速、BatchEvict candidate-selection benchmark。这些能力让数据放置、热点提升、驱逐和评估工具逐步形成闭环，而不是依赖单一的容量阈值策略。

### 4. 结构化对象与远程 tensor 接口扩展

Store 新增 remote tensor batch interfaces；Python wheel 的 structured object 则从 flat MVP 扩展为统一 put/get API、多 buffer structured object put、pool-backed read、schema-guided `DataProto` field encoding 和更完整的非 tensor codec，并恢复多 buffer payload 的 zero-copy put。

这条线直接面向模型服务和数据框架中的复合对象。调用方可以用统一接口处理 tensor、嵌套字段和多段 buffer，减少手工序列化与额外拷贝；schema-guided 编码也为 `DataProto` 等上层数据结构提供更稳定的跨进程表达。

### 5. 新硬件、互联和部署形态继续扩展

Transfer Engine 新增 HPE Slingshot/CXI backend、TPU/PJRT staging、MNNVL Device API 支持，并完善 AMD 场景下的 `rdma+hip` 多协议 segment：单机解耦可组合 RDMA 与 HIP，跨主机目标自动走 RDMA。Store 增加 Sunrise 支持，EP 加入 DeepEP V2 elastic buffer，MUSA 的 EP/PG 构建与发布流程也进一步完善。

这些变化说明 Mooncake 的硬件适配已经不只是“能编译”，而是在向设备发现、staging、跨机路由、P2P 快路径、弹性 buffer 和官方 wheel 发布延伸。不过平台组合快速增加，也意味着每条路径都需要独立的正确性和性能基线。

## 性能优化与可扩展性

### 1. Store 内存、数据放置和驱逐路径优化

Store 启用 NUMA segment 的 hugepage mmap，并优化 HugeTLB 在 RDMA 注册前的 populate 速度，降低大内存区准备成本；tenant id 热路径增加零拷贝规范化；local-first allocation 和 topology-aware replica scoring 则尽量减少不必要的远端访问。Master 默认值也根据 RPC scaling 结果重新调优。

数据路径方面，buffer header 与 slice splitting 被重构，超大 io_uring vector I/O 会被分块处理；structured object 的多 buffer zero-copy put 可减少序列化和复制开销。对长稳运行场景，BatchEvict benchmark、可配置 eviction ratio 和 SSD replay 多线程工具也提供了更可重复的调优手段。

### 2. Transfer Engine 资源和链路利用率优化

Transfer Engine 在多 NIC 注册场景共享单个 dma-buf fd，避免 BAR1 占用随 NIC 数量线性放大；MNNVL/NVLink 在注册时捕获正确 GPU device，并按设备申请 stream，减少 GPU 0 的额外 KMD 流量。MACA P2P copy path、SHM relocation mapping 复用以及 RDMA worker pool 的 post/poll 分离，也分别优化了异构 P2P、共享内存和 RDMA 执行路径。

网络资源控制方面，IBGDA kernel 会限制活跃 RoCE QP 数，TENT 支持 per-pool QP allocation 以及 SL/TC，RailMonitor 改进跨 NUMA rail mapping，RDMA NIC 还可通过 allow/deny list 筛选。这些变化有助于在多卡、多 NIC 和多租户环境中避免 QP、BAR1、线程和链路资源失控。

### 3. 发布、构建和测试效率提升

CI 新增 arm64、TENT CUDA/CPU matrix、AWS EFA wheel、MUSA release/backfill、aarch64 manylinux wheel，并迁移 CUDA release wheel 到 PyTorch manylinux 镜像。wheel build/publish workflow 被抽成可复用流程，同时增加 release branch 测试、pre-release artifact 对齐、EFA 并行度限制与磁盘空间清理。

这些提交主要提升发布覆盖和可重复性。随着 CUDA、PyTorch、EFA、MUSA、aarch64 等矩阵扩张，复用 workflow、固定测试依赖和控制构建资源，比单纯增加更多 job 更能降低长期维护成本。

## 稳定性、Bugfix 与生产化硬化

本期稳定性工作覆盖存储一致性、网络故障、设备上下文和服务生命周期：

- **Store 一致性与磁盘状态**：修复 SSD offload publish-before-commit 竞态、RemoveAll 未清理其他节点 SSD 文件、failed OffsetAllocator eviction 未回滚、local disk snapshot 遗漏总容量、offloading task orphan、S3 list pagination、空 key 和非法 metadata client id 等问题。
- **RDMA 与多 rail 故障恢复**：改进 RDMA NIC failover，刷新 HCA/GID 变化后的 metadata，修复 rail failure 与 CQ timeout 诊断、simultaneous-open timeout、QP ready 前抢先发送、shutdown 时 MR 注销早于 QP teardown，以及连接端点生命周期重复使用问题。
- **NVMe-oF、GDS 与 io_uring 错误传播**：终止 slice failure 会被正确上报，unsupported NVMe-oF task batch 会被拒绝并关联 cuFile completion，GDS batch status 语义和 io_uring stale status 得到修复，避免底层失败被误报为成功或长期停留在旧状态。
- **GPU/异构设备正确性**：修复 TPU 大于 staging chunk 时的静默数据损坏、GPU-addressed local copy 崩溃、AMD 跨节点 RDMA KV transfer、NVLink/MNNVL event-stream device mismatch、Ascend batch worker context、MACA stream API 映射等问题。
- **资源与生命周期**：memory registration 失败时回滚部分注册，ThreadLocalStorage 按实例隔离并回收 holder，Store REST 与 Transfer Engine 支持 SIGTERM/SIGINT 优雅退出，snapshot thread 可及时停止，HTTP/metrics 服务端口绑定失败不再被误报为启动成功。
- **配置与输入校验**：`MooncakeConfig` 字段改为 fail-fast，修复 segment size、`MC_TCP_SLICE_SIZE`、`MC_MS_AUTO_DISC`、SSD boolean、`--host ip:port` 等配置解析边界，并拒绝空 RDMA completion resource 和不支持的 batch。

这些修复共同指向一个趋势：项目在多设备、多 transport、SSD 分层和服务化部署中的异常组合越来越复杂，近期工作重点是让失败能被发现、传播、回滚和恢复，而不是只保证正常路径跑通。

## 接口/API 变化清单（按影响归类）

- **TENT 请求接口**：新增 `IntentType`、`Request.deadline_ns`、`policy_name`，Python binding 同步暴露；SelectionPolicy 支持按 intent 绑定和 SL/TC/QP pool schema。
- **TENT 运维与观测**：transport metrics 增加 label，Transport 暴露 RDMA NIC load stats，配置初始化统一校验并移除失效 metrics flags。
- **Store 多租户**：client tenant id 可配置，引入 canonical `TenantId`、strict quota admission、etcd quota connector、host segment quota pinning 和独立 tenant quota table。
- **Store 数据接口**：新增 remote tensor batch interfaces；`batch_query_keys` 改为只读并返回全部 replica 类型；KV events publisher 可选启用。
- **Python wheel / structured object**：统一 structured-object put/get，支持多 buffer、pool-backed read、schema-guided `DataProto` 编码和非 tensor codec。
- **传输与网络配置**：新增 `MC_FILTER_NIC`/`MC_FILTER_NIC_EXCLUDE`、per-policy SL/TC/QP pool、HPE Slingshot/CXI backend，以及 `rdma+hip` multi-protocol segment。
- **存储策略与运维**：新增 local-first allocation、topology-aware replica scoring、proactive disk watermark eviction、OffsetAllocator FIFO eviction 和持久化恢复。

## 后续关注建议

1. **建立 TENT QoS 的端到端验收基线**：用 mixed traffic workload 验证 EDF、deadline promotion、infeasible drop、带宽降级和 per-pool SL/TC/QP 配置，重点观察尾延迟、饥饿和策略切换抖动。

4. **评估 structured object API 的兼容性和收益**：针对 DataProto、嵌套非 tensor、多 buffer 与大对象比较 zero-copy 命中率、序列化开销和版本兼容性，并给出推荐 schema 与迁移示例。
